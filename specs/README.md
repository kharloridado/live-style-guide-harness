# specs/ — what to read before writing UI code

Read in this order. Colour and spacing govern everything downstream; if those are right, the
component specs follow.

1. `foundations/` — colour, typography, spacing, radius, elevation, iconography, accessibility,
   and `platform.md` (how OutSystems UI and ODC constrain every build).
2. `tokens/token-reference.md` — the closed set of values: every token, its value, when to use
   it. Generated by `npm run specs:tokens`; never edit it by hand.
3. `decisions.md` — rulings and signed-off exceptions. A decision that is not written here gets
   re-flagged on every run.
4. The component or pattern you are touching: `components/<id>.md` or `patterns/<id>.md`.

## Layout

```
specs/
├── foundations/<topic>.md        design rules for the whole system
├── tokens/token-reference.md     generated — the closed token set
├── tokens/<tok-id>/              frozen refs for the token deliverables
├── decisions.md                  rulings and signed-off exceptions
├── components/<cmp-id>.md        the living usage spec — 9 sections, below
├── components/<cmp-id>/          the frozen ref and its evidence
└── patterns/<pat-id>.md, patterns/<pat-id>/
```

The item id prefix decides the folder: `cmp-` → `components/`, `pat-` → `patterns/`,
`tok-` → `tokens/`. `build/lib/specs.mjs` is the one place that rule is coded.

## Two documents per item, and why

| File | What it is | Who changes it |
|---|---|---|
| `<id>.md` | **Usage spec.** How to use what was built: when, which parts, which tokens, which states. | Updated in the same PR as the code it describes. |
| `<id>/ref.md` | **Frozen ref.** The Figma snapshot the build is judged against: provenance, values, conflicts. | Never edited except by a re-snapshot, which is recorded under "Spec updates" inside it. |

The item folder also holds `figma.png` and `variables.json` (the snapshot), `specimen.html` (the
markup the gate measures and the review page renders), `probes.json` and `measurements.json`
(the fidelity probes and the judged baseline).

## Frozen refs

The orchestrator snapshots the ref via the Figma MCP **before** the maker runs, because
subagents have no Figma access. The maker builds to the ref; the checker judges against it;
neither consults live Figma. **No ref means the item goes `needs-human` and is never built.**
A folder with only `NOTES.md` is evidence, not a ref.

- Capture every size variant and every device frame. Figma variables are mode-bound: one name
  can resolve to different values per size or device, and that makes it several tokens, not one.
- A handover note or design-system page that says "single size" or "not responsive" is a claim,
  not evidence. Check it against the file's own size and variant collections.
- The Figma file key is part of the ref. If it differs from `figma.fileKey` in
  `project.config.json`, the ref may be stale — `npm run sync` lists them. Re-snapshot before
  building or judging against old values, and record the superseded key in the new `ref.md`.
- A whole documentation page is usually too large for one `get_design_context` pull: take the
  screenshot and variables, then deep-pull the component-set sublayer and record its node id.
- `get_screenshot` URLs are short-lived: save `figma.png` in the same step.

## Specimens

`specimen.html` is a fragment: the widget as ODC renders it, in every state the ref draws.
`npm run review -- <id>` wraps it in the page the gate measures — the compiled OutSystems UI
base, then `dist/theme.css`, then each `src/blocks` file, then `build/review/specimen.css` — and
publishes it as the review Artifact.

- Use the real rendered widget markup (see `foundations/platform.md`), never an idealised copy.
- `data-gate="hover | active | focus"` holds a cell in that state.
- `<!-- include: <id> -->` renders another item's specimen at that point, one level deep, for
  probes that check a composition or collateral. Position matters: probes that pick
  `nodes[index]` count matches in document order.
- `<script data-src="src/components/x.js"></script>` loads a custom Block's Script the way ODC does;
  follow it with an inline `<script>` that calls `init` for each instance in the specimen.
- Chrome classes are `<<CLASS_PREFIX>>specimen__*` and ship nothing to ODC.
- The review Artifact opens on a **Demo** of the component. It hides `<<CLASS_PREFIX>>specimen__note` and
  `<<CLASS_PREFIX>>specimen__finding` blocks, included specimens, and every section whose heading carries
  `data-review="evidence"` — put that on the `<h3>`/`<h4>` of sibling, collateral and host-mode
  checks. The gate still measures the whole page; "Gate page" in the Artifact shows it.

## Usage spec template

Every `components/<id>.md` and `patterns/<id>.md` has these nine sections, in this order.
Only spec what exists in this project; a small, accurate spec beats a comprehensive stale one.

```markdown
# <Name> — `<id>`

## 1. Metadata
| | |
|---|---|
| Category | Component · restyle of the native OutSystems UI <Widget> (or: custom Block + Script, Pattern) |
| Status | <from loop/state.json> |
| Delivered as | `src/blocks/<file>.css` (Theme CSS) · `src/components/<file>.js` (Script) |
| Frozen ref | [`<id>/ref.md`](<id>/ref.md) |

## 2. Overview
**Use it for** … **Don't use it for** … (and what to use instead)

## 3. Anatomy
The parts, by the OutSystems widget / DOM names a developer sees in ODC Studio.

## 4. Tokens used
| Part | Property | Token |

## 5. Props / API
Widget properties, ExtendedClass modifiers; for a custom Block, its inputs, placeholders, events
and the Script's `init` options and callbacks.

## 6. States
| State | What changes | Notes |
Default, hover, active, focus, disabled, error — "n/a" where the design has none.

## 7. Code example
The OutSystems usage (widget + ExtendedClass) and the rendered HTML it produces.

## 8. Cross-references
Related specs, foundations, findings (FND-NNN) and decisions that constrain it.

## 9. Live Style Guide
| | |
|---|---|
| Page | Restyle of an OutSystems UI pattern: its stock pattern page. New component: its own page, registered in the menu data (never an ad-hoc screen) |
| Definition | One sentence, written for this design system — never the OutSystems UI base pattern's text |
| When to use | "Use the <Name> to …", then "Add the <Block> to the <Placeholder> placeholder." |
| Provenance | "OutSystems UI <Pattern>, restyled" · "New component" · "Wraps <library>" (with link) |
| Preview | The real Block in `Pattern_Preview`, one per variant or state, each widget named; options bound to the real inputs |
| Classes | The class inspector next to each named widget, not a hand-written class list |
| URL | The published page, once it exists |
```

§9 is what the Live Style Guide module shows for this item; the page is built from it. A
component is not done until its page exists, so the handover carries the page as well as the code.

Every token named in a spec must exist in `tokens/token-reference.md` or be a component-scoped
custom property declared in `src/`; `npm run sync` checks. A value the design needs and no token
holds is built as drawn and raised as a finding — say so under §4 with its FND id.

## When to write or change a spec

- New component: add its usage spec before or while building it, in the same PR.
- A component changes: its usage spec is in the same diff. `npm run sync` flags code newer
  than its spec.
- A designer corrects the same thing in two reviews: it is a rule — write it into the
  foundation or the component spec it belongs to.
- A ruling or signed-off exception: add a row to `decisions.md`.
